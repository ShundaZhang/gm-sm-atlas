01 / FIELD NOTES

A correct block core still needs a correct mode

Changing AES to SM4 does not repair a broken nonce policy.

ConstructionMain requirementAuthentication?
ECBRepeated equal blocks expose patterns; only used here for primitive testsNo
CBCUnpredictable IV, defined padding, separate integrity; avoid padding oraclesNo
CTRNever repeat counter/nonce blocks with the same keyNo
GCMNonce uniqueness, tag verification, bounds and associated dataAEAD
CCMCTR plus CBC-MAC with its specified lengths/nonce formatAEAD

ECB, CBC and CTR provide confidentiality functions, not an authenticated application format. CTR nonce reuse repeats a keystream, exposing XOR relationships between plaintexts. GCM nonce reuse can also compromise authentication. AES-GCM and SM4-GCM use a 128-bit block cipher underneath the mode, but produce different outputs and remain different negotiated algorithms.

02 / FIELD NOTES

Use a MAC or AEAD for authenticity

SM3 alone cannot tell whether a sender knew a secret.

HMAC-SM3 uses a 64-byte hash block:
HMAC(K,M)=SM3((K′ XOR opad) || SM3((K′ XOR ipad) || M))
ipad=36 repeated; opad=5c repeated
Normalize K to the hash block width under HMAC rules

Do not create a homemade “SM3 MAC” by prepending or appending a secret. Use the construction selected by the protocol, with separate keys for distinct purposes. An AEAD tag authenticates associated data without encrypting it; that is useful for binding algorithm/version identifiers and message context. Verify the tag before delivering plaintext to an application.

03 / FIELD NOTES

Key length is only one lifecycle property

State, rotation, uniqueness and recovery matter.

Specify key generation, storage, purpose, algorithm identifier, nonce allocation, use limits, rotation and deletion. Coordinate nonce allocation across processes and restarts rather than assuming one counter never resets. Authentication failures should not expose sensitive intermediate plaintext or create distinguishable decryption behavior.
