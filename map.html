01 / FIELD NOTES

Start with the function, not the number

GM names cover several different cryptographic jobs.

FamilyRolePublic learning scope
SM1 / SM7Symmetric block ciphersNames and deployment contexts are public; full round specifications are not part of the open materials used here
SM2ECC signatures, encryption and key exchangePublic arithmetic and protocols; each function needs its own API
SM3256-bit cryptographic hashPublic compression function; no secret key in an ordinary hash
SM4128-bit-key / 128-bit-block cipherPublic S-box, key schedule and 32-round core
SM9Identity-based public-key cryptographyPairing-based signatures, exchange, encapsulation and encryption
ZUCStream-cipher familyKeystream generation and separate confidentiality/integrity profiles

These are the principal named families in this atlas. “All GM algorithms” is not a finite consecutive SM1–SM9 list: industry standards also define constructions, interfaces and protocols. A number gap does not justify inventing an SM5, SM6 or SM8 specification. Legacy or vendor labels need an exact primary specification before comparison.

02 / FIELD NOTES

Treat limited disclosure as a real boundary

Do not fill a missing specification with a guess.

SM1 and SM7 are symmetric algorithm names encountered in cryptographic products; SM7 appears in tag/reader and identification contexts. Public descriptions do not supply enough detail to reconstruct and independently test the full core. This guide therefore explains their category and application boundary without inventing round counts, S-boxes or a universal key-size table.

A closed implementation’s assurance must be evaluated through its documented interface, tested behavior, product scope and applicable assurance evidence. Secrecy of the specification alone is not a security proof. An open-source SM2/3/4 library cannot silently substitute for an SM1/7 device function.

03 / FIELD NOTES

An algorithm, a mode and a protocol are separate layers

SM4, SM4-GCM and a TLS suite are different objects.

The primitive gives a precisely defined transformation. A mode or construction adds nonce handling, authentication or key derivation. A protocol chooses identities, keys, negotiation and message order. A certified module or product adds a further assurance scope. Compare corresponding layers: SM2 signature ↔ ECDSA, SM3 ↔ SHA-256 / SHA3-256, SM4 ↔ AES-128, SM4-GCM ↔ AES-GCM.

SM9 is not another SM2 curve, and ZUC is not a block mode of SM4. Both deserve separate trust and state models.
